# Chromis 1.4.2 (build 10)

Previous release: 1.4.1+9. A **patch** bump with nothing new in the app: a
rewritten README, and the first release uploaded to Google Play by
`.github/workflows/play.yml` rather than by hand. Bumped in `pubspec.yaml` and
`AboutInfo.appVersion`; built on Flutter 3.44.9, as for 1.4.0.

**This is the build that reaches users, not 1.4.1.** Asked through the Play
Developer API before tagging, Play had received bundles 1-6 only: production
is 1.3.0 (versionCode 6), and 1.3.1, 1.4.0 and 1.4.1 never went up. So users
move from 1.3.0 straight to 1.4.2, and `whatsnew-1.4.2.txt` covers both
releases they skip - the 1.4.0 features and the 1.3.1 fixes, merged into one
fixes line to fit Play's 500 characters. The 1.3.1 line about the home-screen
ad and saving was dropped for room. Do not upload 1.4.1 by hand any more.

## What is in it

- **README** rewritten. It still described the milestone plan, a Go Pro
  product id (`pro_remove_ads`) that was never the real one, an interstitial
  on export, Google's test ad ids, MI-GAN as optional and every model as
  Apache-2.0. It now points at the Play listing copy for the feature list,
  because `check_store_listings.py` keeps that one honest and nothing would
  keep a second copy in the README honest.
- **Release workflow.** Publishing a GitHub release tests the tag, builds the
  signed bundle and uploads it to production with the "What's new" from
  `whatsnew-<version>.txt`. Setup is section 6 of
  `docs/release-and-data-safety.md`.

## How it was verified

`flutter analyze` clean, `flutter test` green, and both
`tool/play_release_notes.py` and `tool/check_store_listings.py` pass on the
notes. Before tagging, the service account opened and discarded a Play edit,
and the keystore the GitHub secrets were set from has the same SHA-256 as the
key that signed the 1.4.1 bundle.
